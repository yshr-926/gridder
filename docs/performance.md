# 性能計測手順（issue #57）

spec §14 は「基準データでパン、ズーム、移動、矩形伸縮を継続的に操作できること」「性能判断は実機のフレーム時間と入力遅延を計測して行う」と定める。本書はその計測を再現可能にするための、対象環境・基準データ・取得方法・合格ラインをまとめる。ADR-0003 の「実機計測で目標規模の操作応答性を満たせない」場合にのみ PixiJS 移行を再検討する判断も、ここで得た数値が根拠になる。

計測結果と改善項目は、この手順に沿って測定したうえで GitHub Issue #57 にコメントとして記録する（`docs/performance.md` は手順書であり、実行結果の逐次ログではない。ただし合格ラインの根拠になる代表的な実測値は第 7 節に残す）。

## 1. 対象デスクトップ環境

第一リリースは Chromium 系デスクトップブラウザのみを対象とする（spec §2）。計測もこれに合わせる。

- **ブラウザ**: Chrome（最新安定版）。DevTools Performance パネルを使うため、Chromium 系のうち Chrome を基準にする。
- **OS**: 開発機の OS で構わないが、計測時は他の重い常駐プロセス（ブラウザの他タブ、動画会議、ビルド常駐プロセスなど）を止めた状態で行う。
- **画面**: spec の想定解像度に合わせ 1366x768 または 1440x900（`docs/ui-principles.md` §8 の確認解像度と揃える）。
- **電源**: ノート PC の場合は電源接続し、省電力モードを無効化する（CPU スロットリングで数値が変動するため）。
- **ウィンドウ**: DevTools は別ウィンドウ（docked ではなく `undock`）で開き、アプリのウィンドウサイズが DevTools 分だけ縮まらないようにする。

## 2. 基準データ

`apps/web/src/features/benchmark/generateBenchmarkDocument.ts` が、決定的な擬似乱数（xorshift32、`Math.random` は不使用）で spec §14 の基準データ（約500図形・合計約50,000セル相当）を生成する。同じ seed からは常に同じ文書が生成されるため、計測結果を実行間・マシン間で比較できる。

生成される図形は次の3種類を混在させる（spec §5 の「矩形、凹形状、穴を持てる」を反映）。

- 矩形（`rect`）
- 凹形状の L 字（`lShape`）
- 穴あき矩形（`holedRect`）

### 読み込み方法（開発ビルドと E2E ビルド限定）

開発サーバー（`pnpm --filter @gridder/web dev`）で起動したアプリに `?benchmark` クエリパラメータを付けて開くと、起動直後にセッションが基準データへ差し替わる。

```text
http://localhost:5173/?benchmark        # 既定の 500 図形・約50,000セル
http://localhost:5173/?benchmark=100    # 100 図形（セル数はおよそ比例して縮小）
```

`import.meta.env.DEV` または `VITE_E2E=true` ビルド限定（`apps/web/src/features/benchmark/loadBenchmarkFromQuery.ts`。`__GRIDDER_EDITOR_SESSION__` などのデバッグフックと同じ条件）なので、通常の本番ビルド（`pnpm build` の成果物）では一切発火しない。

**手動計測は `VITE_E2E=true pnpm --filter @gridder/web build && pnpm --filter @gridder/web preview` の本番相当ビルドで行うこと**を推奨する。React の開発ビルドは JSX 要素の生成ごとにデバッグ用のスタック情報を記録するため（#61 の CPU プロファイルではズーム 1 フレームの React 側コストの大半がこれだった）、開発サーバーでの数値は React 側を数倍悲観する。開発サーバーは「どこが重いか」の当たりを付ける用途に使い、合格ラインの判定は本番相当ビルドで行う。

## 3. 指標

### 3.1 フレーム時間（p95）

DevTools Performance パネルで操作中を録画し、メインスレッドの Frames（またはタイムラインの各コミット間隔）からフレーム時間の分布を読み取る。単発の最悪値ではなく **p95**（悪い方から5%を切り捨てた値）を使う。GC や一時的な OS 側の割り込みによる単発の外れ値に判定が引きずられないようにするため。

### 3.2 入力遅延（pointer-down から描画まで）

ユーザーがポインターを押してから、その操作を反映した最初のフレームが画面に出るまでの時間。DevTools の `Interactions` トラック（Chrome の Performance パネルが記録する `pointerdown` などのイベント）と、直後の `Frame` の開始時刻の差から読み取る。

## 4. 合格ライン

| 指標 | 合格ライン | 根拠 |
| --- | --- | --- |
| フレーム時間 p95 | 16.7ms 以下 | 60fps（1000ms / 60 ≈ 16.7ms）を「継続的に操作できる」の具体化とする。Konva はカーソル中心ズーム・パン・ドラッグにアニメーションを付けない設計（spec §4, §6.1, ui-principles §6）なので、操作中の各フレームがそのまま知覚される。60fps を割ると直接操作の追従にコマ落ちを感じ始める。 |
| 入力遅延 | 50ms 以下 | Google の RAIL モデルは「ユーザー操作への応答は100ms以内」を目安にするが、これは知覚できる遅延の上限であり、Gridder のような直接操作（ドラッグで追従する UI）は遅延の影響をより強く受ける。半分の50msを目標にすることで、100msの上限に対して十分な余裕を確保する。 |

いずれも基準データ（約500図形・約50,000セル）に対して、パン・ズーム・移動・矩形伸縮の**継続操作中**（ドラッグの最初のフレームだけでなく、ドラッグを続けている間）に成立している必要がある。単発の操作開始時だけ基準を満たし、ドラッグを続けると悪化する場合は不合格として扱う。

不合格の場合は、ADR-0003 の「Reconsider When」に従い、Konva ノード数、React 再レンダリング、Zustand の購読範囲、hit graph のいずれがボトルネックかを DevTools の Bottom-Up / Call Tree で特定してから Issue #57 に記録し、必要なら改善用の別 Issue を切る。PixiJS への再評価は、この特定を経てからの判断とする。

## 5. 測定手順

1. `pnpm --filter @gridder/web dev` で開発サーバーを起動する。
2. `http://localhost:5173/?benchmark` を開き、基準データが読み込まれたことを確認する（図形が画面いっぱいに表示される）。
3. DevTools を開き、Performance パネルに切り替える。CPU スロットリングは既定（無効）のままにする（第一リリースの対象環境そのものを計測するため）。
4. 録画（●）を開始し、次の操作を順に行う。各操作は2〜3秒程度、途中で止めずに継続する。
   1. **パン**: 中ボタンドラッグまたは `Space + ドラッグ` で画面を左右に往復させる。
   2. **ズーム**: マウスホイールでズームイン・ズームアウトを繰り返す。
   3. **移動**: 図形をクリックしてドラッグで大きく移動させる。
   4. **矩形伸縮**: 矩形を選択し、角のハンドルをドラッグして伸縮させる。
5. 録画を停止する。
6. タイムライン上部の Frames 行から各操作区間のフレーム時間を読み取り、区間ごとに p95 を算出する（DevTools の "Timings" や個々の "Frame" エントリの duration を手動集計するか、後述の自動計測スクリプトの出力を使う）。
7. `Interactions` トラックで `pointerdown` を選び、直後の `Frame` 開始時刻との差を入力遅延として記録する。パン・移動・伸縮それぞれで最低1回ずつ確認する。
8. 結果を第4節の合格ラインと照合し、Issue #57 にコメントする（コメント文面の下書きは本 Issue に対応する worker のレポートを参照）。

## 6. 自動計測（補助、CI 必須ではない）

`apps/web/e2e/specs/performance-benchmark.spec.ts` に、実際のポインター操作を伴う自動計測がある。実機での目視確認・DevTools 手動計測を置き換えるものではなく、リグレッションの早期発見と改善前後の比較を補助する位置づけのため、既存 CI には組み込んでいない。

```bash
# 開発サーバー（Vite dev）に対して計測。当たりを付ける用途
pnpm --filter @gridder/web exec playwright test \
  --config=playwright.benchmark.config.ts --project=chromium --grep "@issue-57"

# 本番相当ビルド（VITE_E2E=true でビルドして vite preview）に対して計測。合格ライン判定はこちら
BENCH_TARGET=preview pnpm --filter @gridder/web exec playwright test \
  --config=playwright.benchmark.config.ts --project=chromium --grep "@issue-57"
```

### 6.1 測り方

- ページ内に `requestAnimationFrame` ループのプローブ（`apps/web/src/features/benchmark/frameProbe.ts`）を仕込み、連続するコールバックの間隔をフレーム時間として記録する。rAF はメインスレッドがフレームを処理できるときにしか呼ばれないため、この間隔はユーザーが知覚するフレーム時間そのものになる。
- 各フレームで、前フレーム以降に到着した最も古いポインター／ホイールイベントの `timeStamp` からの経過時間を「入力→フレーム」として記録する。第 3.2 節の入力遅延の近似値。
- `PerformanceObserver` の Long Task（50ms 以上）も併記する。Long Task がゼロなのにフレームが遅い場合は、メインスレッド外（canvas のラスタや合成）が原因と切り分けられる。
- パン（中ボタンドラッグ）、ズーム（ホイール）、移動（図形の内側をドラッグ）、矩形伸縮（角ハンドルをドラッグ）を、各 2.5 秒間（`BENCH_GESTURE_MS`）ポインターを往復させ続けて計測する。ステップ数ではなく時間で区切るので、フレームが遅いほど処理できた入力数（`inputs/s`）が減り、それも結果に表れる。
- 各ジェスチャーの前に「連続 10 フレームが 50ms 未満」になるまで待ち、初回描画の残りを計測に混ぜない。
- 既定はインストール済み Google Chrome のヘッドあり（第 1 節の対象環境に合わせる）。`BENCH_HEADLESS=1` でヘッドレス、`BENCH_BROWSER=chromium` で Playwright 同梱 Chromium。ヘッドレスは GPU ラスタがソフトウェア寄りになり数値がやや悪化するので、合格ライン判定はヘッドありで行う。
- 専用ポートは 5299（5199 はエディタの補助プロセスが占有していることがあった）。

### 6.2 以前の測り方が信頼できなかった理由

#57 時点のこのテストは CDP の `Tracing` で compositor の `BeginFrame` イベント間隔を集計し、p95 10.09ms を報告していた。しかし `BeginFrame` はメインスレッドが停止していても vsync ごとに発火するため、実機では計測すら困難な状態（#61 の症状）でも約 16ms 刻みの綺麗な分布が得られてしまう。フレーム時間の判定にこの方式は使わない。

## 7. 実測記録（issue #61）

500 図形 / 47,610 セルの基準データ。数値は第 6 節の自動計測の p95（ms）。「入力→フレーム」は第 3.2 節の入力遅延の近似値。開発機は Apple Silicon Mac、Chrome 安定版、ウィンドウ 1440x900。

### 7.1 改善前（開発サーバー）

| 操作 | フレーム p95 | 入力→フレーム p95 | 備考 |
| --- | --- | --- | --- |
| パン | 187.6 | 185.6 | 中ボタンドラッグ。1 秒に 10 回しか入力を処理できない |
| ズーム | 92.7 | 160.4 | |
| 移動 | 96.5 | 100.8 | |
| 矩形伸縮 | 98.6 | 99.0 | |

初期描画直後は数秒間フレームが出ず、安定待ちを入れないと計測にならなかった（Issue 本文の「DevTools での計測すら困難」に相当）。

### 7.2 原因の内訳

Konva だけで `stage.x()` を動かして `draw()` し、`getImageData` でラスタを強制した実験（React を経由しない）では、1 フレーム約 100ms のうち JS（Konva の描画コマンド記録）が約 9ms、残り約 93ms が図形レイヤーの canvas ラスタだった。ラスタは GPU プロセス側で行われるため Long Task にも JS プロファイルにも現れない。原因は Konva の `perfectDrawEnabled`（既定 true）で、fill と stroke を持ち opacity < 1 の Shape ごとに全画面のバッファキャンバスへ描いてから合成する。500 図形 × 全画面合成が毎フレーム走っていた。

同じ理由で、共有画像用に常時マウントされている `ExportStage`（描画範囲の実寸、基準データでは 6180x7220px、最大 4 レイヤー）の再描画が 1 回約 4 秒かかり、文書のコミットごとに数秒フレームが止まっていた。

残りは Issue 本文の分析どおり、`GridCanvas` が `offset` / `scale` を購読していることによる毎フレームの React 再レンダリングだった。

### 7.3 改善後

| 操作 | 本番相当ビルド・ヘッドあり Chrome（判定用） | 本番相当ビルド・ヘッドレス | 開発サーバー・ヘッドあり |
| --- | --- | --- | --- |
| パン | **10.0**（入力→フレーム 7.0） | 17.4（16.6） | 9.8（8.6） |
| ズーム | **8.2**（12.8） | 21.7（33.6） | 72.9（79.8） |
| 移動 | **5.1**（4.3） | 18.8（17.1） | 32.9（32.8） |
| 矩形伸縮 | **5.8**（4.9） | 19.6（18.0） | 26.3（25.9） |

判定用の列はすべて第 4 節の合格ライン（フレーム p95 16.7ms 以下、入力遅延 50ms 以下）を満たす。Long Task はゼロ。ヘッドレスはソフトウェア寄りのラスタで一律に数 ms 悪化する。開発サーバーのズーム・移動・伸縮は React 開発ビルドのオーバーヘッド（第 2 節）で、CPU プロファイルではその大半が `jsxDEV` だった。

段階ごとの効果（開発サーバー・ヘッドレス、p95、パン / ズーム / 移動 / 伸縮）:

| 段階 | パン | ズーム | 移動 | 伸縮 |
| --- | --- | --- | --- | --- |
| 改善前 | 187.6 | 92.7 | 96.5 | 98.6 |
| `perfectDrawEnabled=false`（ADR-0005） | 72.6 | 80.1 | 99.9 | 99.6 |
| パンを React から分離、グリッド量子化 | 19.7 | 97.5 | 102.7 | 126.0 |
| ShapesLayer 配下の memo 化、注釈の 1/scale Group 化と省略 | 19.4 | 93.4 | 48.1 | 40.8 |

`ExportStage` の再描画は約 4 秒から 18ms になった（`perfectDrawEnabled` の効果。書き出し体験 #56 にも効く）。

### 7.4 見た目への影響

`perfectDrawEnabled=false` により、半透明図形の境界線（1.5px）の内側半分が塗りとブレンドされてわずかに濃くなる。サブピクセル幅で、キャンバスと共有画像の両方に同じ差が出る。判断の経緯は ADR-0005 と `ShapePolygon.tsx` のコメントを参照。

注釈は、図形の画面上の短辺がフォントサイズ（12px）未満になると描かない（`annotationLegibility.ts`）。ズームアウトで文字が図形より大きくなる領域だけが対象で、ズームインすれば戻る。
