# 性能計測手順（issue #57）

spec §14 は「基準データでパン、ズーム、移動、矩形伸縮を継続的に操作できること」「性能判断は実機のフレーム時間と入力遅延を計測して行う」と定める。本書はその計測を再現可能にするための、対象環境・基準データ・取得方法・合格ラインをまとめる。ADR-0003 の「実機計測で目標規模の操作応答性を満たせない」場合にのみ PixiJS 移行を再検討する判断も、ここで得た数値が根拠になる。

計測結果と改善項目は、この手順に沿って測定したうえで GitHub Issue #57 にコメントとして記録する（`docs/performance.md` 自体は手順書であり、実行結果のログではない）。

## 1. 対象デスクトップ環境

第一リリースは Chromium 系デスクトップブラウザのみを対象とする（spec §2）。計測もこれに合わせる。

- **ブラウザ**: Chrome（最新安定版）。DevTools Performance パネルを使うため、Chromium 系のうち Chrome を基準にする。
- **OS**: 開発機の OS で構わないが、計測時は他の重い常駐プロセス（ブラウザの他タブ、動画会議、ビルド常駐プロセスなど）を止めた状態で行う。
- **画面**: spec の想定解像度に合わせ 1366x768 または 1440x900（`docs/ui-principles.md` §8 の確認解像度と揃える）。
- **電源**: ノート PC の場合は電源接続し、省電力モードを無効化する（CPU スロットリングで数値が変動するため）。
- **ウィンドウ**: DevTools は別ウィンドウ（docked ではなく `undock`）で開き、アプリのウィンドウサイズが DevTools 分だけ縮まらないようにする。

## 2. 基準データ

`apps/web/src/features/benchmark/generateBenchmarkDocument.ts` が、決定的な擬似乱数（xorshift32、`Math.random` は不使用）で spec §14 の基準データ（約500図形・合計約50,000セル相当）を生成する。同じ seed からは常に同じ文書が生成されるため、計測結果を実行間・マシン間で比較できる。

生成される図形は次の3種類を混在させる（spec §5 の「矩形、凹形状、穴を持てる」を反映）。

- 矩形（`rect`）
- 凹形状の L 字（`lShape`）
- 穴あき矩形（`holedRect`）

### 読み込み方法（開発ビルド限定）

開発サーバー（`pnpm --filter @gridder/web dev`）で起動したアプリに `?benchmark` クエリパラメータを付けて開くと、起動直後にセッションが基準データへ差し替わる。

```text
http://localhost:5173/?benchmark        # 既定の 500 図形・約50,000セル
http://localhost:5173/?benchmark=100    # 100 図形（セル数はおよそ比例して縮小）
```

`import.meta.env.DEV` 限定（`apps/web/src/features/benchmark/loadBenchmarkFromQuery.ts`）なので、本番ビルド（`pnpm build` の成果物、および Playwright が使う `pnpm preview`）では一切発火しない。本番相当のビルドで計測したい場合は、後述の Playwright スモーク計測を使うか、`generateBenchmarkDocument()` の結果を `window.__GRIDDER_EDITOR_SESSION__.reset(document)`（dev / `VITE_E2E=true` ビルドで公開される、issue #42 由来のデバッグフック）から手動で読み込む。

## 3. 指標

### 3.1 フレーム時間（p95）

DevTools Performance パネルで操作中を録画し、メインスレッドの Frames（またはタイムラインの各コミット間隔）からフレーム時間の分布を読み取る。単発の最悪値ではなく **p95**（悪い方から5%を切り捨てた値）を使う。GC や一時的な OS 側の割り込みによる単発の外れ値に判定が引きずられないようにするため。

### 3.2 入力遅延（pointer-down から描画まで）

ユーザーがポインターを押してから、その操作を反映した最初のフレームが画面に出るまでの時間。DevTools の `Interactions` トラック（Chrome の Performance パネルが記録する `pointerdown` などのイベント）と、直後の `Frame` の開始時刻の差から読み取る。

## 4. 合格ライン

| 指標 | 合格ライン | 根拠 |
| --- | --- | --- |
| フレーム時間 p95 | 16.7ms 以下 | 60fps（1000ms / 60 ≈ 16.7ms）を「継続的に操作できる」の具体化とする。Konva はカーソル中心ズーム・パン・ドラッグにアニメーションを付けない設計（spec §4, §6.1, ui-principles §6）なので、操作中の各フレームがそのまま知覚される。60fps を割ると直接操作の追従にコマ落ちを感じ始める。 |
| 入力遅延 | 50ms 以下 | Google の RAIL モデルは「ユーザー操作への応答は100ms以内」を目安にするが、これは知覚できる遅延の上限であり、Gridder のような直接操作（ドラッグで追従する UI）は遅延の影響をより強く受ける。半分の50msを目標にすることで、100msの上限に対して十分な余裕を確保する。 |

いずれも基準データ（約500図形・約50,000セル）に対して、パン・ズーム・移動・矩形伸縮の**継続操作中**（ドラッグの最初のフレームだけでなく、ドラッグを続けている間）に成立している必要がある。単発の操作開始時だけ基準を満たし、ドラッグを続けると悪化する場合は不合格として扱う。

不合格の場合は、ADR-0003 の「Reconsider When」に従い、Konva ノード数、React 再レンダリング、Zustand の購読範囲、hit graph のいずれがボトルネックかを DevTools の Bottom-Up / Call Tree で特定してから Issue #57 に記録し、必要なら改善用の別 Issue を切る。PixiJS への再評価は、この特定を経てからの判断とする。

## 5. 測定手順

1. `pnpm --filter @gridder/web dev` で開発サーバーを起動する。
2. `http://localhost:5173/?benchmark` を開き、基準データが読み込まれたことを確認する（図形が画面いっぱいに表示される）。
3. DevTools を開き、Performance パネルに切り替える。CPU スロットリングは既定（無効）のままにする（第一リリースの対象環境そのものを計測するため）。
4. 録画（●）を開始し、次の操作を順に行う。各操作は2〜3秒程度、途中で止めずに継続する。
   1. **パン**: 中ボタンドラッグまたは `Space + ドラッグ` で画面を左右に往復させる。
   2. **ズーム**: マウスホイールでズームイン・ズームアウトを繰り返す。
   3. **移動**: 図形をクリックしてドラッグで大きく移動させる。
   4. **矩形伸縮**: 矩形を選択し、角のハンドルをドラッグして伸縮させる。
5. 録画を停止する。
6. タイムライン上部の Frames 行から各操作区間のフレーム時間を読み取り、区間ごとに p95 を算出する（DevTools の "Timings" や個々の "Frame" エントリの duration を手動集計するか、後述の自動計測スクリプトの出力を使う）。
7. `Interactions` トラックで `pointerdown` を選び、直後の `Frame` 開始時刻との差を入力遅延として記録する。パン・移動・伸縮それぞれで最低1回ずつ確認する。
8. 結果を第4節の合格ラインと照合し、Issue #57 にコメントする（コメント文面の下書きは本 Issue に対応する worker のレポートを参照）。

## 6. 自動スモーク計測（補助、CI 必須ではない）

`apps/web/e2e/specs/performance-benchmark.spec.ts` に、Chrome DevTools Protocol (CDP) 経由でフレーム時間を自動取得するスモークテストがある。実機での目視確認・DevTools 手動計測を置き換えるものではなく、リグレッションの早期発見を補助する位置づけのため、既存 CI には組み込んでいない。

```bash
pnpm --filter @gridder/web exec playwright test \
  --config=playwright.benchmark.config.ts --project=chromium --grep "@issue-57"
```

このテストは開発サーバー（`?benchmark` クエリパラメータが効くビルド）に対して実行する想定のため、既存の `playwright.config.ts`（本番相当の `pnpm run preview` を対象にする）とは別に `playwright.benchmark.config.ts` を用意し、専用ポート（5199）で Vite dev サーバーを起動する。既存 e2e スイートの大半は旧セルベース UI を前提にしており失敗する状態にあるため（`docs/spec.md` 移行が完了する #58 まで）、`--grep` で本スペックだけを単独実行できるようにしてある。

このテストは `?benchmark=500`（spec §14 の基準データそのもの）に対して実行を確認済みで、開発機での実測は p95 フレーム時間 10.09ms（70フレーム捕捉）だった。第4節の合格ラインを満たす値だが、この自動計測は CDP の `BeginFrame` トレースイベントから機械的に算出した近似値であり、対象デスクトップ環境での手動計測（本書 第5節）の代替にはならない。
